# Goal Restate — 目标与问题复述

目的：在继续工作之前，用你自己的话把对用户意图的理解完整摆出来，让用户能一眼看出哪里理解对了、哪里偏了。这是一次对齐检查，不是执行任务。

## 1. 基本原则

- **用自己的话**：不要照抄或轻微改写用户原话。换一种表述方式才能暴露理解偏差。
- **区分来源**：明确哪些是用户明说的，哪些是你推断的。推断内容必须标注，并说明推断依据。
- **目标与问题分开**：目标是用户想达到的状态；问题是阻碍用户达到该状态的东西。两者常被混为一谈，需分别陈述。
- **深挖一层**：不止复述表层请求（"要做 X"），还要说出你认为的深层动机（"做 X 是为了 Y"）。
- **不执行任务**：本次只复述与对齐，不写代码、不修改文件、不给出解决方案。
- **简洁**：每一项用一到三句话说清，不堆砌。

## 2. 信息来源

基于当前会话中可获得的全部上下文：用户的消息、已读取的文件、已执行的命令及其输出、之前的讨论与决策。若会话上下文不足以形成有意义的复述，直接说明缺什么，并向用户提问，而不是编造。

## 3. 输出结构

按以下顺序输出：

### 3.1 目标

- **表层目标**：用户直接要求做的事。
- **深层目标**：你认为用户真正想达成的结果，以及为什么想要它。

### 3.2 问题

- **要解决的问题**：当前阻碍目标实现的具体问题是什么。
- **问题的成因**（如已知）：你理解的问题为什么存在。
- **问题边界**：哪些属于本次要解决的范围，哪些不属于。

### 3.3 成功标准

你认为满足什么条件时，用户会认为这件事完成了。尽量写成可验证的形式。

### 3.4 约束与偏好

用户明确提出或从上下文可推断的限制：技术栈、风格、不能改动的部分、时间或范围限制等。

### 3.5 推断与假设

列出你在理解过程中做出的、用户没有明说的假设，每条附上依据。这是最容易出错的部分，需尽量写全。

### 3.6 歧义与待确认点

列出你不确定、存在多种理解方式的地方。每条给出你的倾向性理解，以及其他可能的理解。

## 4. 收尾

输出完毕后，请用户：

1. 指出复述中理解错误或不完整的部分；
2. 对"歧义与待确认点"逐条确认。

用户回复后，根据修正更新你的理解，用简短的一段话给出修正后的最终版本（只写变化的部分及最终结论，不要重复全部结构）。确认对齐后，再回到原本的工作流程中。
