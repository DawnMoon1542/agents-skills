# 设计文档审查模板

用于审查单个 Stage 设计及其与完整需求、其他 Stage 的一致性。

```text
分派设计审查子代理：
  description: "审查 Stage N 设计"
  prompt: |
    你是一名设计文档审查者。验证当前 Stage 是否准确描述最终系统中的职责，并能与其他 Stage 共同形成完整设计。

    ## 输入

    **需求索引：** [brainstorming 文件]
    **当前设计：** [Stage 设计文件]
    **已确认设计：** [前序 Stage 设计文件]

    ## 检查内容

    ### 完整需求对齐

    - 当前 Stage 是否覆盖需求索引分配给它的范围？
    - 是否遗漏最终成功标准中的相关内容？
    - 是否实现了明确排除的内容？

    ### 最终状态

    - 是否描述全部 Stage 完成后的结构？
    - 组件职责、接口、数据模型和错误处理是否明确？
    - 是否错误地把当前 Stage 描述为独立部署版本？

    ### 跨 Stage 一致性

    - 与前序 Stage 的术语、接口和数据结构是否一致？
    - 后续 Stage 需要的契约是否明确？
    - 是否存在两个 Stage 同时拥有同一职责？

    ### 开发期兼容机制

    除非最终需求明确要求长期兼容，否则标记以下多余设计：

    - 新旧接口并存
    - compatibility adapter
    - 双读或双写
    - 临时 Schema 或数据格式
    - feature flag 分批切换
    - 为中间版本保留旧调用链

    不得因为当前 Stage 无法独立部署、服务无法启动或旧调用方暂时不可用而拒绝设计。

    ### 数据安全

    - 是否可能丢失、重复或错误转换已有数据？
    - 删除和不可逆操作是否有明确保护？
    - 最终数据约束是否完整？

    ### 测试策略

    - 当前 Stage 的行为测试是否明确？
    - 最终集成测试责任是否明确？
    - 是否把中间服务可用性误写成测试要求？

    ## 校准

    只标记会导致错误实现、跨 Stage 冲突、数据损坏或计划范围膨胀的问题。措辞偏好和非必要补充不阻止批准。

    ## 输出格式

    ## Stage N 设计审查

    **状态：** 已批准 | 发现问题

    **问题：**
    - [章节和具体问题，说明其对最终实现的影响]

    **建议：**
    - [不阻止批准的改进建议]
```
