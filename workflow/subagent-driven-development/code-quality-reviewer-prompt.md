# 代码质量审查者提示词模板

仅在规格审查通过后使用。审查 Task BASE_SHA 与当前未提交工作区之间的差异。

```text
分派代码质量审查子代理：
  description: "审查 Task N 的代码质量"
  prompt: |
    你正在审查 Task N 的实现质量。规格审查已经通过。

    ## 输入

    **Task 摘要：** [Task 目标]
    **Stage 设计：** [相关设计章节]
    **Task BASE_SHA：** [Task 开始前 SHA]
    **测试结果：** [红阶段和绿阶段结果]

    ## 审查范围

    读取：

    - `git status --short`
    - `git diff --stat BASE_SHA`
    - `git diff BASE_SHA`
    - 状态中列出的全部新增未跟踪文件

    只审查当前 Task 产生的差异，不标记未修改的既有问题。

    ## 检查内容

    ### 正确性

    - 当前 Task 的逻辑是否正确？
    - 边界和错误条件是否处理？
    - 是否存在数据损坏或无声吞错？

    ### 清晰度和维护性

    - 命名是否准确并符合 CONTEXT？
    - 函数和文件职责是否清晰？
    - 是否存在重复、不必要抽象或混乱控制流？
    - 是否遵循代码库已有模式？

    ### 测试质量

    - 是否观察到正确红阶段？
    - 当前 Task 的目标测试是否通过？
    - 测试是否验证真实行为而不是只验证 mock？
    - 正常、边界和错误场景是否覆盖？

    ### 文件范围

    - 是否只修改计划允许的文件？
    - 新文件是否有明确职责和公共接口？
    - 是否遗漏直接调用方检查？

    ### 最终状态优先

    除非最终设计明确要求长期兼容，否则标记新旧接口并存、adapter、双读双写、临时 Schema、feature flag 迁移和旧调用链保留。

    当前 Task 无法完整构建、服务无法启动或无法独立部署不是质量问题，前提是未完成集成明确属于后续 Task。当前 Task 自身测试失败、计划外失败或数据风险仍是阻塞问题。

    ## 输出格式

    - **优势：** [具体实现优点]
    - **严重问题：** [文件和行号]
    - **重要问题：** [文件和行号]
    - **次要问题：** [文件和行号]
    - **评估：** APPROVED | NEEDS_CHANGES
```
