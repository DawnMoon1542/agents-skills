# 测试驱动开发

对有实际行为影响的改动，先建立能区分当前行为与目标行为的最小验证，再编写实现并保持验证通过。验证可以是单元测试、集成测试、命令级检查、渲染检查或其他与产物匹配的可重复检查。

**核心原则：** 验证必须能说明目标行为是否成立，规模与改动影响相称。测试和生产代码一样需要长期维护和运行，只有失败时意味着真实问题的测试才值得写。不要为了满足形式上的红阶段编写没有实际保护作用的测试。

```text
失败测试 → 验证失败原因 → 最小实现 → 目标测试通过 → 整理 → 再次通过
```

## 适用范围

| 场景 | 行为 |
|---|---|
| 新功能 | 属于“必须有测试”类别的行为编写针对性测试；其余按“测试取舍”使用更轻量的检查 |
| bug 修复 | 优先添加可重现问题的回归测试；已有可靠覆盖时复用它 |
| 修改已有行为 | 先修改覆盖该行为的已有测试，使其因旧行为失败，再改实现；不新建平行测试 |
| 删除行为 | 删除只验证该行为的测试，确认没有残留引用；不编写“已删除”测试 |
| 行为重构 | 复用已有测试；缺少覆盖且属于“必须有测试”类别时先补测试 |
| 纯文档、静态资源、配置与生成文件 | 不写测试，使用与产物匹配的检查，例如渲染、构建、lint 或类型检查 |

## 测试取舍

按以下顺序判断：

1. 这个测试失败时，用户或调用方会遇到什么问题？说不出具体问题就不写。
2. 属于“不写测试”类别时不写，改用表中的验证方式。
3. 已有测试覆盖目标行为时，修改或扩展已有测试。
4. 否则在最近的稳定公共边界写一个测试。

### 必须有测试

新增或修改以下行为时必须有测试保护：

| 类别 | 示例 |
|---|---|
| 数据迁移与持久化 | schema 迁移、存储格式、序列化往返、不可逆删除 |
| 安全与权限边界 | 鉴权、授权、路径穿越、输入校验、敏感信息脱敏 |
| 并发与故障恢复 | 状态机、重试、取消、超时、锁、崩溃后恢复 |
| 跨组件契约 | 前后端 API、RPC 与事件格式、跨进程或跨服务的文件格式 |
| 有分支的业务规则 | 解析、计算、转换、权限判断等复杂纯逻辑 |
| 已发生缺陷的回归 | 能重现该缺陷的最小用例 |

### 不写测试

| 类别 | 典型写法 | 改用 |
|---|---|---|
| 文档、规则、提示词文本 | 断言文档包含某段文字 | 人工审查 |
| 源码文本 | 读取源码断言包含或不包含某个标识符、导入或调用 | lint、类型检查、代码审查 |
| 工具与工程配置 | 断言依赖已声明、配置项存在、脚本列出某个命令 | 工具自身报错、构建 |
| 已删除的行为 | 断言接口、文件、字段或组件已不存在 | 删除对应测试 |
| 框架与第三方库行为 | 验证框架路由、ORM、校验库本身可用 | 不验证 |
| 无逻辑代码 | 纯透传、纯数据结构、常量、类型定义 | 类型检查 |
| 实现细节 | mock 调用次数、内部调用顺序、私有函数、模块拆分 | 测试公共边界上的行为 |
| 样式与文案 | CSS 类名、布局、颜色、界面文案 | 渲染检查或人工检查 |
| 重复用例 | 与已有测试走同一分支，只换输入值 | 合并为一个测试或参数化 |

删除操作是为了收紧安全边界时，测试“匿名或越权请求被拒绝”这一当前行为，不测试代码已删除。提示词或规则中由程序解析的结构按跨组件契约处理，只测试解析结果，不测试措辞。

### 数量与层级

- 一个目标行为一个测试。边界和异常只在进入不同分支或产生不同结果时各写一个，不为凑齐“正常、边界、异常”三类编写同一等价类的用例。
- 在稳定的公共边界测试：服务接口、HTTP 路由、组件的用户可见行为。内部辅助函数只有本身是复杂纯逻辑时才单独测试。
- 先查找已有测试。已有测试覆盖目标行为时修改或扩展它，不新建平行测试文件。
- 测试描述最终行为。只在某个后续 Task 之前成立的中间状态不写测试。
- 测试名和测试文件名描述业务行为，不包含 Stage、Task、Phase 或计划编号；计划与测试的对应关系写在计划里。
- 项目有慢测试标记时，需要真实子进程、网络、浏览器或较长等待的测试按约定标记。

## 验证范围

验证范围应与改动影响相称。目标检查通过后，只有出现新改动、新失败或未解决疑点时，才扩大或重复验证。

### 先建立有效验证

验证应尽量：

- 只验证一个明确行为
- 名称描述业务结果
- 使用真实代码，除非外部系统使 mock 无法避免
- 包含清晰输入、输出和错误断言
- 在目标行为缺失时失败，或明确证明现有实现已经满足目标

如果验证一开始就通过，先检查它是否真正覆盖目标行为。覆盖成立时记录为已有行为，不修改正确断言来制造失败。因语法、导入或环境错误中止的测试不能证明行为成立。

### 绿：实现目标行为

编写使当前测试通过的最小最终实现：

- 不添加测试未要求的能力
- 不为开发期间保持服务运行而添加兼容层
- 不保留随后会删除的临时接口
- 遵循设计定义的最终命名和结构

### 重构：保持目标测试通过

只在目标测试通过后：

- 移除重复
- 改进命名
- 提取必要辅助函数
- 删除失效代码

整理后再次运行相同测试。

## smart-exec-plan 中的验证边界

smart-exec-plan 连续执行全部 Stage。Task 和 Stage 不是部署边界，因此当前 Task 的绿色状态只要求其计划规定的目标测试通过。

中间 Task 可以存在：

- 尚未迁移的调用方
- 暂时失败的完整构建
- 暂时无法启动的服务
- 将由后续已定义 Task 完成的集成

这不允许当前 Task 忽略自身失败。以下情况仍须立即修正：

- 当前 Task 新增或修改的测试失败
- 失败与后续 Task 无关
- 出现计划外错误
- 数据可能丢失或损坏
- 测试通过依赖虚假断言或过度 mock

全部 Stage 完成后必须运行完整验证，届时不得保留任何中间失败。

## bug 修复

```text
重现 bug 的失败测试
→ 确认测试因该 bug 失败
→ 最小修复
→ 回归测试通过
→ 相关测试通过
```

行为明确且可复现时，优先在生产代码前补回归测试。若测试框架或问题性质不适合，使用最小可重复检查记录复现和修复结果，不为了形式完整而增加测试。

## 测试质量

好的测试应具备：

- **最小**：一个测试只表达一个行为
- **清晰**：名称说明预期结果
- **敏感**：业务规则改变时相关测试会失败
- **稳健**：行为不变的重构不会让测试失败
- **真实**：验证真实代码交互，而不是只验证 mock
- **稳定**：不依赖任意等待时间和共享状态

测试是行为规格，不是覆盖率装饰。无法写出准确验证时，先判断是否应改用集成测试、快照、渲染检查或命令级 smoke test；只有目标行为本身无法定义时，才停止并检查设计。

mock 使用、仅测试用方法和变更探测器测试等反模式见同目录 `testing-anti-patterns.md`。

## 禁止做法

- 对需要回归保护的行为先写实现后补测试
- 保留预先写好的实现作为参考再声称采用 TDD
- 验证一开始就通过却未检查其是否真正覆盖目标
- 把导入错误当作正确红阶段
- 为了通过测试修改正确断言
- 只测试 mock 调用次数而不测试行为
- 用宽泛快照代替关键业务断言
- 断言文档、源码或配置的文本内容
- 为已删除的行为编写“保持删除”测试
- 为凑齐正常、边界、异常三类编写同一等价类的测试
- 为只在后续 Task 之前成立的中间状态编写测试
- 在测试名或测试文件名中使用 Stage、Task 或计划编号
- 为中间服务可用性增加最终不需要的兼容代码
- 在最终验证失败时以“中间状态”为理由继续

## Task 完成检查

- 已建立与改动相称的有效验证
- 新增测试都属于“必须有测试”类别，且不与已有测试重复
- 被改变或删除的行为对应的旧测试已更新或删除
- 若采用红阶段，已确认失败原因是目标行为缺失
- 已实现设计规定的最终行为
- 当前 Task 的目标测试通过
- 整理后测试仍通过
- 没有计划外改动
- 没有纯开发过渡兼容代码
