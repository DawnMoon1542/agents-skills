# 计划文档审查模板

用于审查单个 Stage 计划，并验证全部计划能够连续实现最终设计。

```text
分派计划审查子代理：
  description: "审查 Stage N 实现计划"
  prompt: |
    你是一名计划文档审查者。验证当前 Stage 计划是否可执行、符合设计，并且没有为了开发期间保持服务运行而增加过渡兼容工作。

    ## 输入

    **需求索引：** [brainstorming 文件]
    **当前设计：** [Stage 设计文件]
    **当前计划：** [Stage 计划文件]
    **其他 Stage 设计和计划：** [文件列表]

    ## 检查内容

    ### 设计覆盖

    - 当前 Stage 的每项设计职责是否有对应 Task？
    - 是否遗漏接口、数据、错误处理或测试要求？
    - 是否实现需求索引明确排除的内容？

    ### Task 分解

    - 每个 Task 是否适合一次实现、审查和提交？
    - 文件、函数、类型、行为和测试是否具体？
    - Task 依赖和 Group 顺序是否明确？
    - 是否错误地要求 Task 或 Stage 独立部署？

    ### TDD 可执行性

    - 行为变更是否先安排失败测试？
    - 是否写明测试场景、断言和失败原因？
    - 当前 Task 的验证范围是否明确？
    - 是否误将全仓库通过设为每个 Task 的必要条件？

    ### 开发期兼容机制

    除非最终设计明确要求长期兼容，否则标记以下多余内容：

    - 新旧接口并存
    - compatibility adapter
    - 双读或双写
    - 临时 Schema 或临时数据格式
    - feature flag 分批迁移
    - 仅用于保持中间服务可用的 Task
    - 先创建、后续又删除的过渡代码

    不得因为中间 Task 无法完整构建、启动或部署而拒绝计划。

    ### 数据安全和最终状态

    - 是否保护持久化数据不被丢失、重复或错误转换？
    - 最后一个 Stage 后是否没有遗留旧实现和临时代码？
    - 全部计划是否共同覆盖最终成功标准？
    - 完整验证命令是否真实且集中在全部 Stage 完成后运行？

    ### 提交边界

    - 每个 Task 是否提供一个符合仓库规范的提交信息？
    - 计划是否避免单独的进度提交？
    - 是否把提交操作错误地写成 Task Step？

    ## 校准

    只标记会导致错误实现、执行阻塞、数据损坏、最终验证缺失或范围膨胀的问题。中间状态不可部署不是问题。

    ## 输出格式

    ## Stage N 计划审查

    **状态：** 已批准 | 发现问题

    **问题：**
    - [Task 和 Step，具体问题及影响]

    **建议：**
    - [不阻止批准的改进建议]
```
