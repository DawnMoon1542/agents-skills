# 分支总结与双视角 review

回答两个问题：这个分支到底做完了什么，以及它是否真的达成了原本的目标、实现得是否站得住。

分支简报（`branch-brief`）面向他人交接，本技能面向判定。两者可先后执行，本技能不重复简报的叙述性内容，只输出结论与依据。

**开始时声明：** “我正在使用 branch-review 技能总结当前分支并执行双视角 review。”

## 适用与不适用

适用：

- 合并前验收，判断能否交付
- 分支开发中断后判断完成了哪些部分、剩下什么
- 判断"计划都勾完了"是否等价于"目标已达成"
- 长分支的阶段性复盘

不适用：

- 只需向他人说明变更内容：使用 `branch-brief`
- 只需逐条比对文档与代码：使用 `audit-and-grill`
- 只在改动范围内找 bug 与质量问题：使用 `code-review`

## 1. 确定审查基线

```bash
git rev-parse --abbrev-ref HEAD
git merge-base <BASE_REF> HEAD
git rev-parse HEAD
git status --short
git log --oneline --no-merges <BASE_SHA>..HEAD
```

`BASE_REF` 的确定顺序与 `branch-brief` 一致：用户指定 → 远端默认分支 → `origin/main` / `main` / `master`。

本技能关注三种基线，职责不同，不可混用：

| 基线 | 用途 |
|---|---|
| `BASE_SHA` | 分支全部改动范围 |
| `IMPLEMENTATION_BASE_SHA` | 排除纯文档提交后的实现差异起点 |
| 需求文档中的目标 | 判定"目的完成"的基准，不是 Git 引用 |

分支由 smart-exec-plan 执行时，`IMPLEMENTATION_BASE_SHA` 应从执行报告或文档提交 commit 推导；无法确定时使用 `BASE_SHA` 并注明差异包含文档提交。

## 2. 收集目标声明

"目的"必须来自真实文档，不能由审查者自行归纳。按以下顺序找：

1. brainstorming 需求索引：目标、成功标准、明确排除项
2. 各 Stage 设计文件：最终状态定义、接口契约
3. 各 Stage 计划文件：Task 清单与进度勾选
4. ADR：已确认的架构约束
5. 分支自身 commit message：仅作为补充，不作为判定基准

没有需求文档时明确告知用户：本技能只能做代码质量视角，目的完成度无法判定。不要用"看起来像是要解决 X"替代文档基准。

把目标拆成可判定的原子声明，格式与 `audit-and-grill` 第 1 步一致。计划勾选状态不构成实现证据。

## 3. 汇总变更内容

按主题归纳分支做了什么，粒度比 `branch-brief` 更粗，只保留能映射到目标声明的主题：

```bash
git diff --stat <BASE_SHA>..HEAD
git diff --numstat <BASE_SHA>..HEAD
git diff --summary <BASE_SHA>..HEAD
```

每个主题记录：做了什么、落点模块、对应哪几条目标声明、对应 commit 范围。无法映射到任何目标声明的改动单独列出，标记为"计划外改动"，等待第 5 步判定。

## 4. 一致性审计（内联 audit-and-grill）

对第 2 步的每条目标声明执行 `audit-and-grill` 的第 1 至第 4 步：

1. 抽取声明并记录来源路径与行号
2. 采集直接证据：读取实现、测试、调用方，必要时运行可复现命令
3. 判定为一致 / 矛盾 / 缺失 / 无法验证
4. 对矛盾、缺失、无法验证的结论分派独立复核者，尝试推翻

复核模板直接使用 `<audit-and-grill 技能目录>/references/grill-prompt.md`。复核者只拿到声明原文与判定结果，不拿审查者推理。

一致性结果按四条目标逐条给出，不做整体折算。

## 5. 目的完成度判定

综合一致性结果后回答三类问题：

**已达成**：声明判定为一致，且有直接证据与复核确认。

**未达成**：判定为矛盾或缺失。写明缺什么、影响哪条成功标准。

**计划外**：分支实现了目标未要求的改动，或明确排除的功能被实现。分两类处理：
- 无害补充（测试、文档、必要的重构）：记录，不阻塞
- 需求外功能或中间态遗留（新旧接口并存、adapter、双读双写、临时 schema、feature flag 分批切换、旧调用链）：判为问题，纳入结论

完成度结论用三种之一，不允许模糊表述：

| 结论 | 条件 |
|---|---|
| COMPLETE | 全部必达目标一致，无阻塞性计划外改动 |
| PARTIAL | 存在未达成目标，但属于明确承诺的后续 Stage 或用户确认延后 |
| INCOMPLETE | 存在未达成目标且没有承接方 |

"计划勾选全部完成"但存在缺失声明时，结论必须是 INCOMPLETE，并指出勾选与实际不符。

## 6. 代码质量审查

只审查本分支产生的差异，不报告未修改的既有问题。审查维度：

| 维度 | 检查内容 |
|---|---|
| 正确性 | 逻辑、边界与错误条件、静默吞错、数据丢失或重复转换 |
| 数据安全 | 迁移可逆性、最终约束、批量操作保护 |
| 清晰度 | 命名与术语表是否一致、职责边界、重复实现、不必要抽象 |
| 模式一致 | 是否遵循代码库既有组织方式与错误处理约定 |
| 测试质量 | 是否有真实行为断言、正常/边界/错误路径覆盖、是否只断言 mock |
| 最终状态 | 是否残留过渡代码、未迁移调用方、被绕过的旧实现 |
| 可维护性 | 注释解释"为什么"、技术债是否标记、是否有无法解释的 hack |

按严重程度分三级：阻塞、重要、次要。阻塞项必须给出文件与行号、触发条件、失败后果。

跨 Stage 集成单独检查：组件接口、数据结构、错误类型是否一致，数据流是否贯通，是否存在断连调用链。

## 7. 分派审查者

规模较大时用 subagent 或 workflow 并行，三个视角互相独立：

| 视角 | 输入 | 输出 |
|---|---|---|
| 目标视角 | 需求索引、设计、计划；一致性判定结果 | 每条目标的达成状态与证据 |
| 质量视角 | `IMPLEMENTATION_BASE_SHA..HEAD` 差异 | 阻塞/重要/次要问题清单 |
| 集成视角 | 全部 Stage 的交付物与调用方 | 断连调用、契约不一致、重复职责 |

分派规则：

- 每个审查者只拿自己视角需要的上下文，不转发其他视角的结论
- 审查者读取实际差异与代码，不信任计划勾选与历史报告
- 审查者不修改任何文件，不执行 Git 写操作
- 同一结论出现分歧时保留双方判断，不取平均

审查结论必须可复现：给出文件路径加行号、可运行命令或具体输入。

## 8. 输出

默认写入 `docs/reviews/YYYY-MM-DD-<branch-slug>.md`；用户只要求查看时直接输出到对话。

```markdown
# 分支 review：<分支名>

## 结论

- 目的完成度：COMPLETE / PARTIAL / INCOMPLETE
- 代码质量：可合并 / 有条件合并 / 不可合并
- 阻塞项：N 项
- 一句话：<能否交付，卡在哪>

## 基线

- 基线：<BASE_REF> @ <BASE_SHA>
- 实现起点：<IMPLEMENTATION_BASE_SHA>
- HEAD：<HEAD_SHA>
- 规模：N 个文件，+X / -Y 行，M 个 commit

## 分支做了什么

### <主题一>
- 内容：
- 模块：
- 对应目标：<声明 id 列表>
- commit：

## 目的完成度

| 目标声明 | 判定 | 证据 | 复核 | 状态 |
|---|---|---|---|---|

未达成项说明：<缺什么、影响哪条成功标准、是否有承接方>

计划外改动：<内容与判定>

## 代码质量

### 阻塞
- <文件:行号> <问题> <触发条件与后果>

### 重要

### 次要

## 集成检查

<跨 Stage 接口、数据流、调用链结论>

## 遗留与建议

<不阻塞但需要跟进的内容，按严重程度排序>
```

## 判定纪律

- 目标来自文档，不来自审查者的直觉
- 勾选状态不是实现证据
- 没有证据时判定为"无法验证"，不默认通过
- 计划外功能与过渡代码必须纳入结论，不能因为"反正能用"放过
- 目的完成度与代码质量分开判定，不因质量好而放松目的要求，也不因目的达成而忽略质量问题

## 禁止事项

- 用 commit message 代替读实际差异
- 审查未修改的既有代码并把既有问题算进本分支
- 修改代码或提交
- 把无法验证的条目计入已达成
- 用"整体质量不错"替代分级问题清单
